## Directive captured so far

This is a mandatory engineering repair, not a UI design task. Do not merely add components, patch individual screens, declare success because the build passes, declare success because Supabase functions exist, or declare success because a page loads. The stated systemic problem is that the frontend is not reliably reflecting the actual Supabase backend state and capabilities. The required task is to find the root cause, fix the architecture, and make the existing frontend a true live client of the existing backend.

## Phase 0 — Stop and investigate before changing code

Do not modify code immediately. First perform a complete forensic audit of the GitHub repository, current production branch, current production deployment, Vercel configuration, Supabase project, database schema, migrations, RPC/functions, RLS policies, storage buckets and policies, frontend services, React components, React state/data providers, routes, API/RPC calls, environment variables, build configuration, and deployment configuration. Determine exactly why the frontend continues displaying content or functionality that is not actually coming from Supabase and why backend functionality is not appearing in the UI. Do not guess, assume, or patch symptoms. Find the root bug.

## Phase 1 — Find the data source of every screen

For every frontend page, determine where its data comes from. Trace the chain:

DATABASE → SUPABASE RPC / QUERY → SERVICE → HOOK / STATE → COMPONENT → CARD → SCREEN

For every displayed entity, identify whether it comes from Supabase, hardcoded data, mock data, fallback data, static JSON, cached data, local state, an incorrect query, an incorrect environment, or a failed backend request. Create a report and do not continue until this has been identified.

## Phase 2 — Remove the root cause of mock content

Search the entire repository for: mock, dummy, demo, sample, fixture, fake, fallback, placeholder, seed, hardcoded, and static. Also search for equivalent structures such as `const EVENTS`, `const ARTISTS`, `const SONGS`, `const VENUES`, and `const TICKETS`, plus known fictional/demo artist and event names.

Remove all production rendering paths that can display fictional or demo entities. Do not delete cards, sections, or UI. Retain cards, pills, boards, tabs, headers, sections, layout, navigation, backgrounds, watermarks, spacing, typography, and responsive design. Replace only the data source.

The directive explicitly rejects fallback data that can repopulate empty live collections. The intended architecture is live Supabase data through the existing UI structure, with genuine loading, empty, error, and success states.

## Acceptance principle

The implementation must trace and repair the full chain from Supabase/RPC/RLS through the frontend service, React state, component, card, screen, user click, database mutation, and UI refresh. Build success alone is not sufficient evidence.

## Phase 2 — Remove the root cause of mock content

The directive requires replacing fallback expressions such as `liveData.length ? liveData : MOCK_DATA` with direct live data. When zero records exist, retain the existing card frame and show an appropriate empty state; never invent data.

## Phase 3 — No silent fallbacks

Remove dangerous patterns including `liveData || fakeData`, `liveData.length ? liveData : demoData`, `catch(() => mockData)`, fallback catalogs, static artist lists, and static event lists. A failed Supabase request must not silently become fake content. The required state chain is REQUEST → LOADING → SUCCESS with real data → EMPTY with empty state → ERROR with error state. The forbidden state is ERROR → FAKE DATA.

## Phase 4 — Verify Supabase connection

Verify that the production frontend uses the correct Supabase URL, anon/publishable key, project, schema, environment, and deployment variables. Confirm local development and production are not pointing to different projects. Print the actual project reference used during build without exposing secrets, and verify that Vercel production uses the intended environment.

## Phase 5 — Verify database reality

Inspect actual database counts for users, profiles, artists, artist profiles, organizers, venue managers, event staff, admins, events, venues, songs, albums, music videos, ticket types, orders, tickets, reservations, notifications, posts, comments, ratings, likes, wallets, role applications, and verification applications. The UI must reflect these actual records.

## Strict acceptance rule

The build passing or a page loading is not enough. The complete data path must be proven from Supabase through RPC/RLS, service, React state, component, card, screen, user click, database mutation, and UI refresh. Any missing link must be repaired at the architectural source.
